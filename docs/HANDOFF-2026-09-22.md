## What this session did

Started from `docs/HANDOFF-2026-09-21.md`'s instruction to read the latest Build & Test
run on main. That run (and the three before it, going back to the scaffold push
`195da92`) had never actually started — `gh api .../actions/runs/<id>/jobs` showed
`runner_id:0` on every one, and the queue time on the last one had grown to 3h40m+
(HANDOFF-2026-09-21 flagged this exact shape as possibly a minutes/billing problem and
said to check before iterating).

**It was not a billing problem.** Cross-checking `build.yml`/`deploy.yml`'s
`runs-on: macos-27` against GitHub's `actions/runner-images` published catalog showed
`macos-27` is not a real label — the Xcode 27 preview image is published as `xcode-27`
(and `xcode-27-xlarge`). An unmatched hosted-runner label produces exactly this
symptom: the job queues forever with no runner ever assigned, instead of failing fast.
This was confirmed directly (fetched the runner-images README), not guessed. The
Actions spending limit was never touched or even queried — no `gh auth refresh`, no
billing page read; the fix didn't need it.

Fixed the label (commit `994e577`) and the queue resolved within seconds. Two more
real build-config bugs surfaced once it actually ran, fixed forward in small commits
(3 executing runs total, well inside the "~3 before switching trigger mode" budget —
never needed to touch `build.yml`'s `push` trigger):

1. `994e577` — `runs-on: macos-27` → `xcode-27` in both `build.yml` and `deploy.yml`.
2. `84378e7` — `StoryCueTests` and `StoryCueDuoTests` both left `PRODUCT_NAME` unset in
   `project.yml`, so both resolved to an empty product name and collided on the same
   `PlugIns/.xctest` output path the moment the scheme built both together
   ("Multiple commands produce..."). Gave each an explicit `PRODUCT_NAME`.
3. `30696c0` — the app module built without `-enable-testing`, so `StoryCueTests`
   couldn't `@testable import StoryCue` ("Unable to resolve Swift module dependency").
   A hand-authored XcodeGen project doesn't inherit the `ENABLE_TESTABILITY=YES`
   default an Xcode-created project's template bakes into Debug — added it explicitly
   under `settings.configs.Debug` in `project.yml`.

**Final green: run `35676600490`.** Confirmed it's the *correct* baseline-only green,
not an accidental one — the job summary reads exactly: iphoneos SDK **27.0**, Duo SDK
headers **NO** (compile flag **NOT SET**), Duo simulator device type **NO**. That
matches what today's runner image should produce; if a future green shows SDK 27.1 or
the flag SET, that's a real event (the Duo lane turning on), not noise.
